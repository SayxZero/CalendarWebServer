# CalendarWebServer

Бэкенд сайта «Космос календаря» — веб-версии планера
([CalendarWeb](https://github.com/SayxZero/CalendarWeb)). Он отдаёт страницу
сайта и передаёт её запросы серверу синхронизации
([CalendarServer](https://github.com/SayxZero/CalendarServer)): аккаунты сайта —
это аккаунты сервера, а события, задачи, привычки и календари — те же записи,
что у планера на компьютере и телефоне.

Сам он ничего не хранит. Сайт для сервера синхронизации — ещё одно устройство
аккаунта: говорит его протоколом (`/api/sync` и соседи), и все правила —
ревизии, «побеждает более поздняя правка», общие календари и их конфликты,
защита от подбора пароля — остаются там. Бэкенд добавляет то, что нужно
браузеру:

- **ключ сеанса в HttpOnly-cookie**, а не в странице: скрипт, пробравшийся в
  страницу, его не прочтёт;
- **проверку, что изменяющий запрос пришёл со страницы сайта** (свой заголовок
  и `Origin`), cookie с `SameSite=Strict`;
- **белый список маршрутов**: только то, чем пользуется планер;
- **свой счёт неверных паролей** — по адресу посетителя, раньше общего счёта
  сервера синхронизации (за сайтом все посетители для него — один адрес);
- **заголовки безопасности** (CSP только со своего адреса, без фреймов).

Как сайт и бэкенд устроены и почему так — в [DesDoc.md](DesDoc.md); как всё
работает вместе с планером и сервером — в `DESDOC.md` зонтичного репозитория
[CosmosCalendar](https://github.com/SayxZero/CosmosCalendar).

## Сборка

Нужен .NET 10 SDK; сторонних пакетов у самого сервера нет (только
`Microsoft.AspNetCore.App` из .NET), у тестов — MSTest.

```bash
dotnet build CalendarWebServer.sln
dotnet test CalendarWebServer.sln
```

На Windows одной командой — собрать и запустить:

```bat
run-web.bat                                  :: порт 8780, сервер синхронизации 127.0.0.1:8765
run-web.bat -p 8781 -u 127.0.0.1:8766        :: тестовый сервер рядом с рабочим
```

Готовая к переносу папка (сервер, `appsettings.json` и сайт в `site\`):

```bat
publish.bat                 :: в publish\
publish.bat -out D:\web     :: в другую папку
```

Опубликованному серверу нужен ASP.NET Core Runtime 10; сайт он находит в
`site` рядом с собой.

## Запуск

```bash
CalendarWebServer                                   # порт 8780, сервер синхронизации 127.0.0.1:8765
CalendarWebServer -p 8780 -u 192.168.0.146:8765     # сервер синхронизации на другой машине
CalendarWebServer --web-root ../CalendarWeb/site    # сайт из другой папки
CalendarWebServer --help
```

| Параметр | `appsettings.json` | По умолчанию | Что это |
|---|---|---|---|
| `-p`, `--port` | `Web:Port` | 8780 | порт сайта |
| `--host` | `Web:Host` | все адреса | слушать один адрес (`127.0.0.1` — только эта машина) |
| `-u`, `--upstream` | `Web:Upstream` | `127.0.0.1:8765` | сервер синхронизации: `host:port` или `https://…` |
| `-w`, `--web-root` | `Web:WebRoot` | `site` рядом, иначе `CalendarWeb/site` зонтика | папка сайта |
| `--public-server` | `Web:PublicServerAddress` | адрес из `--upstream` | адрес сервера синхронизации в ссылках общего доступа для планера |
| `--secure-cookie` | `Web:SecureCookie` | `auto` | `auto` — Secure, если запрос пришёл по HTTPS; `always`, `never` |
| `--trusted-proxy` | `Web:TrustedProxies` | — | прокси, которому верить в `X-Forwarded-For`/`-Proto` |
| — | `Web:SyncTimeoutSeconds` | 60 | сколько ждать обмена и запросов общего доступа |
| — | `Web:RequestTimeoutSeconds` | 15 | сколько ждать остальных запросов |
| — | `Web:MaxBodyMegabytes` | 64 | предел тела запроса (обмен с мелодиями — самый большой) |

## Развёртывание

- **Дома.** Бэкенд на той же машине, что и сервер синхронизации:
  `CalendarWebServer -u 127.0.0.1:8765 --public-server 192.168.0.146:8765`.
  `--public-server` — адрес, который знают планеры: он попадает в ссылку
  общего доступа `calendar-planner://share?server=…`.
- **Снаружи.** Перед бэкендом — обратный прокси с TLS (nginx, Caddy), бэкенд
  слушает `127.0.0.1`, а прокси назван в `--trusted-proxy 127.0.0.1`: тогда
  cookie получает `Secure`, а счёт неверных паролей идёт по настоящему адресу
  посетителя. Сервер синхронизации наружу открывать не обязательно.
- Бэкенду не нужны права администратора и доступ к базе сервера
  синхронизации — только сетевой доступ к его порту.

## API

Страница говорит с бэкендом так:

| Запрос | Что делает бэкенд |
|---|---|
| `GET /web/config` | `{service, version, serverAddress}` — адрес сервера для ссылок общего доступа |
| `GET /web/health` | спрашивает `/api/ping` сервера синхронизации; 200 или 502 |
| `POST /api/login`, `/api/register` | передаёт серверу; ключ сеанса из ответа кладёт в cookie `cosmos_session`, странице — ответ без ключа |
| `POST /api/logout` | передаёт серверу с ключом и забывает cookie, что бы тот ни ответил |
| `GET /api/ping`, `/api/me`, `/api/record`, `/api/share`, `/api/share/peek`; `POST /api/profile`, `/api/password`, `/api/sync`, `/api/share`, `/api/share/member`, `/api/share/link`, `/api/share/join`, `/api/share/leave` | передаёт серверу с `Authorization: Bearer <ключ из cookie>`; ответ — как есть, с `Retry-After` и `Allow` |

Тела запросов и ответов — как у сервера синхронизации (README
CalendarServer, «API»). Свои ответы бэкенда — того же вида
`{"error": "<код>", "message": "<по-русски>"}`:

| Код | Когда |
|---|---|
| 401 `unauthorized` | запрос аккаунта без cookie — до сервера он не доходит; ответ сервера 401 ещё и стирает cookie |
| 403 `forbidden` | изменяющий запрос без заголовка `X-Requested-With: CosmosCalendarWeb` или с чужим `Origin` |
| 404 `not_found`, 405 `method` | маршрута нет в списке / не тот метод (`Allow`) |
| 429 `throttled` | у этого посетителя слишком много неверных паролей (`Retry-After`) |
| 502 `upstream` | сервер синхронизации недоступен |
| 504 `upstream_timeout` | сервер синхронизации не ответил вовремя |

## Безопасность

- Ключ сеанса — в cookie `HttpOnly`, `SameSite=Strict`, `Secure` за HTTPS,
  на год (столько ключ живёт на сервере без использования).
- Ключ, присланный самой страницей в `Authorization`, не принимается — только
  cookie.
- Изменяющие запросы требуют своего заголовка: чужая страница не может
  поставить его без предварительного запроса CORS, а бэкенд таких не разрешает.
- Неверные пароли: 5 на логин и 20 на адрес посетителя за 10 минут.
  Сервер синхронизации считает по адресу соединения, а за сайтом это адрес
  бэкенда — его пределы (10 и 50) общие для всех посетителей сайта, поэтому
  свой предел ниже.
- В журнал пишутся адрес, метод, путь, код и время — без строки запроса (в
  ней бывает токен ссылки) и без ключей.

## Тесты

```bash
dotnet test CalendarWebServer.sln
```

24 теста (MSTest). Бэкенд поднимается на свободном порту перед поддельным
сервером синхронизации, который отвечает как настоящий и запоминает, что до
него дошло: cookie и ключ, заголовок и `Origin`, белый список, ограничитель
входа, 401 и выход, `Retry-After`, недоступный сервер, раздача сайта и
заголовки. Один тест работает с настоящим сервером — только с переменной
`WEB_TEST_SERVER=<адрес>` **тестового** экземпляра (он регистрирует там
аккаунт):

```bash
WEB_TEST_SERVER=127.0.0.1:8766 dotnet test CalendarWebServer.sln
```

## Структура

```
src/CalendarWebServer/
  Program.cs          командная строка, справка
  WebServerApp.cs     сборка приложения: Kestrel, прокси, сайт, /web/*
  WebOptions.cs       настройки (раздел Web)
  ApiRoutes.cs        белый список маршрутов сервера синхронизации
  ApiProxy.cs         передача /api/*: cookie, CSRF, ограничитель, ошибки
  SessionCookie.cs    cookie сеанса
  LoginThrottle.cs    счёт неверных паролей по посетителю
  SecurityHeaders.cs  заголовки безопасности
  appsettings.json    настройки по умолчанию
tests/CalendarWebServer.Tests/
  Harness.cs          бэкенд перед поддельным сервером синхронизации
  ProxyTests.cs       тесты прокси, cookie, ограничителя, раздачи
  RealServerTests.cs  с настоящим сервером (WEB_TEST_SERVER)
run-web.bat, publish.bat
```
