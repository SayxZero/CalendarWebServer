# CalendarWebServer — описание архитектуры и реализации

Бэкенд сайта «Космос календаря». Инструкции по сборке и запуску — в
[README.md](README.md), заметки для агента — в [CLAUDE.md](CLAUDE.md). Сайт —
отдельный репозиторий [CalendarWeb](https://github.com/SayxZero/CalendarWeb),
его устройство здесь не описывается (оно в его `DesDoc.md`); как сайт, планер и
сервер синхронизации работают вместе — `DESDOC.md` зонтичного репозитория
[CosmosCalendar](https://github.com/SayxZero/CosmosCalendar).

## 1. Назначение и границы

Сайт работает с теми же аккаунтами и записями, что планеры. Бэкенд при этом
**не хранит ничего своего** и не открывает базу сервера синхронизации: он
передаёт запросы страницы серверу по его HTTP API и добавляет то, без чего
браузер нельзя пускать к этому API напрямую.

### 1.1 Почему через HTTP API, а не прямо к `server.db`

Решение принято вместе с владельцем проекта (28.10.2026). Рассматривались два
пути.

**Прямой доступ к базе** — бэкенд на Qt C++, собранный из исходников
`Storage`/`ShareStore` сервера, как админ-панель. Против него:

- **второй писатель рядом с сервером.** Сервер держит `server.lock` — «один
  сервер на базу» — и фиксирует правки своим потоком групповой записи
  (`Storage::Committer`) за мьютексом ворот записи; второй процесс ждал бы его
  только `busy_timeout`'ом SQLite, а правильность курсора ревизий держится на
  том, что он читается внутри транзакции записи одного процесса;
- **состояние в памяти сервера**: счёт неверных паролей, счёт обменов,
  отметки использования ключей — их пришлось бы повторять или терять;
- **права и место**: база службы лежит в `%ProgramData%`, открытой только
  администраторам и службе, — бэкенду нужны были бы те же права и та же
  машина;
- **сцепка со схемой**: каждая смена схемы сервера требовала бы пересборки
  бэкенда;
- и главное — **логику планера всё равно писать заново**: сервер не разбирает
  записи (поле `data` для него непрозрачно), повторения, выполнение задач,
  привычки живут только в планере.

**Через HTTP API** сайт — ещё одно устройство аккаунта. Все правила остаются в
одном месте, CalendarServer не меняется, бэкенд не требует прав. Цена —
лишний сетевой шаг (бэкенд и сервер стоят на одной машине, так что он
дешёвый) и аккаунт в памяти страницы, который она берёт целиком при каждом
открытии (данных у личного планера мало). В браузере ничего из аккаунта не
хранится, и режима «нет связи» у сайта нет: без сервера нет и бэкенда.

### 1.2 Почему .NET

Выбор владельца из того, что установлено на машине (Node.js 24, .NET 10,
Qt 6.5): ASP.NET Core даёт зрелый HTTP-стек, cookie, проверку заголовков
прокси и раздачу файлов без сторонних пакетов — только общий фреймворк
`Microsoft.AspNetCore.App`. Тесты — MSTest.

## 2. Устройство

```
браузер ──HTTP──► CalendarWebServer ──HTTP──► CalendarServer ──► server.db
           site/*   │  статические файлы сайта
           /web/*   │  config, health
           /api/*   └► ApiProxy: cookie → Bearer, CSRF, белый список, ограничитель входа
```

| Файл | Что делает |
|---|---|
| `WebServerApp.cs` | собирает приложение: настройки (файл + командная строка), Kestrel, заголовки прокси, конвейер, раздачу сайта |
| `WebOptions.cs` | раздел `Web` настроек, адрес сервера синхронизации как URI, адрес для ссылок |
| `ApiRoutes.cs` | маршруты сервера синхронизации, которые пропускаются, и их вид (открытый, вход, выход, аккаунт) |
| `ApiProxy.cs` | передача запроса: проверки, сборка запроса к серверу, разбор ответа |
| `SessionCookie.cs` | cookie `cosmos_session`: чтение, запись, удаление |
| `LoginThrottle.cs` | счёт неверных паролей по посетителю |
| `SecurityHeaders.cs` | CSP и остальные заголовки каждого ответа |

## 3. Передача запроса (`ApiProxy`)

Порядок проверок — от дешёвых к дорогим, и ни одна отвергнутая просьба не
доходит до сервера синхронизации:

1. **Маршрут.** Путь собирается из `PathBase` и `Path` (`app.Map("/api")`
   отрезает префикс) и ищется в `ApiRoutes` точным совпадением: неизвестный —
   404, известный не тем методом — 405 с `Allow`. Новый маршрут сервера
   закрыт, пока его не добавят в таблицу: сайт получает ровно то, чем
   пользуется планер.
2. **Откуда пришёл изменяющий запрос.** Всё, кроме `GET`, обязано нести
   `X-Requested-With: CosmosCalendarWeb`, а `Origin`, если браузер его прислал,
   должен быть этим самым сайтом. Свой заголовок чужая страница не поставит без
   предварительного запроса CORS, а на него бэкенд не отвечает разрешением; с
   cookie `SameSite=Strict` это закрывает подделку запросов.
3. **Ключ.** Запрос аккаунта без cookie — 401 сразу. Ключ, который страница
   прислала в `Authorization` сама, не учитывается: ключ существует только в
   cookie.
4. **Вход.** Для `login`/`register` — счёт неверных паролей (раздел 5).

Запрос к серверу собирается заново: метод, путь и строка запроса как есть, тело
байт в байт, `Authorization: Bearer <ключ из cookie>`, `X-Forwarded-For` и
`X-Forwarded-Proto` (сервер их пока не читает, раздел 7). Ожидание — 60 секунд
для обмена и общего доступа (столько ждёт планер), 15 — для остального;
нет ответа — 504, нет соединения — 502.

Ответ уходит странице как есть, с `Retry-After` и `Allow`, со своими
поправками:

- **вход и регистрация** — ключ из ответа уходит в cookie, а из тела
  вынимается; ответ без ключа при успехе — 502 (сервер повёл себя не так, как
  обещает протокол);
- **выход** — cookie стирается при любом ответе: ключ, который сервер уже не
  знает, всё равно что забыт;
- **401 на запрос аккаунта** — cookie стирается, страница просит войти снова,
  как планер (`AuthFailed`).

## 4. Cookie сеанса

`cosmos_session`: `HttpOnly`, `SameSite=Strict`, `Path=/`, `Max-Age` — год
(ключ, которым не пользовались год, сервер удаляет сам). `Secure` — по
настройке `SecureCookie`: `auto` ставит его, когда запрос пришёл по HTTPS
(за доверенным прокси — по `X-Forwarded-Proto`). Значение проверяется на вид
ключа (base64url, до 256 знаков) — мусор в cookie не уходит серверу.

## 5. Неверные пароли (`LoginThrottle`)

Сервер синхронизации считает неверные пароли по адресу соединения и паре
«адрес и логин» (10 и 50 за 10 минут). За бэкендом адрес соединения у всех
посетителей один — адрес бэкенда, — и эти пределы становятся общими для всего
сайта. Поэтому бэкенд считает сам, по адресу посетителя, и с пределами ниже:
**5** на пару «посетитель и логин», **20** на посетителя, окно — 10 минут.
Неудачей считается 401/403 на вход; удачный вход забывает неудачи этой пары.
Отказ — 429 `throttled` с `Retry-After` до момента, когда старые неудачи выйдут
из окна. Ключи, по которым давно не ошибались, вычищаются раз в окно.

Остаётся ограничение: несколько посетителей с разных адресов вместе всё ещё
могут закрыть один логин *на сайте* (у планеров с других адресов вход
остаётся). Снять его может только сервер синхронизации, научившись верить
`X-Forwarded-For` от названных прокси.

## 6. Сайт и заголовки

Папка сайта ищется так: настройка `WebRoot`; `site` рядом с программой
(опубликованная сборка); `CalendarWeb/site` вверх по дереву от программы
(рабочая копия зонтика). Без папки бэкенд работает, только страницу не отдаёт.
Файлы отдаются с `Cache-Control: no-cache` — у сайта нет сборки с хешами в
именах, поэтому браузер каждый раз сверяется (`ETag`, 304) и новая версия
видна сразу.

Каждый ответ несёт `Content-Security-Policy` (всё — только со своего адреса;
стили допускают `style` атрибуты, без которых нельзя задать цвет календаря у
элемента), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
`Referrer-Policy: no-referrer` и `Permissions-Policy`. Ответы `/api/*` —
`Cache-Control: no-store`.

## 7. Чего нет и что дальше

- **Служба Windows** не сделана: пакета `Microsoft.Extensions.Hosting.
  WindowsServices` нет в общем фреймворке, а ставить службы на машине разработки
  нельзя. Бэкенд запускается в консоли (`run-web.bat`) или опубликованным;
  на Linux — под systemd как обычная программа.
- **`X-Forwarded-For` на сервере синхронизации** — снял бы ограничение раздела 5.
- **Установщик** в пакетах выпуска (`build-packages.ps1`) бэкенд пока не
  собирает.

## 8. Тесты

`tests/CalendarWebServer.Tests` — MSTest. `Harness` поднимает две программы на
свободных портах: поддельный сервер синхронизации (минимальное приложение
ASP.NET, которое отвечает на маршруты планера так, как отвечает настоящий, и
складывает увиденные запросы — метод, путь, `Authorization`,
`X-Forwarded-For`, тело) и сам бэкенд перед ним с временной папкой сайта.
Клиент — `HttpClient` с `CookieContainer`, как браузер.

`RealServerTests` запускается только с `WEB_TEST_SERVER`: регистрирует аккаунт
на тестовом сервере, отправляет запись обменом, читает её `/api/record`,
выходит и проверяет, что cookie больше не действует.
